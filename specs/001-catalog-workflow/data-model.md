# Catalog workflow data model

Status: proposed implementation contract, based on [spec.md](spec.md) and the lead decisions in
[research.md](research.md). No schema migration, application code, database operation, or verification
has been executed for this document. Field names below are specification choices, not recovered
implementation facts.

## Ownership and persistence boundary

One seeded synthetic workspace owns every processing run. The Go SaaS Manager resolves that workspace
from trusted startup configuration. Browser input never supplies a workspace identifier. The database
contains application-owned records only; the workspace is not a representation of an authenticated
user or a claim of demonstrated multi-tenant access control.

The Go bootstrap creates one PostgreSQL connection pool and passes narrow persistence dependencies
to the modules that need them. The Connector Manager owns the catalog workflow. Its source interface
provides raw CSV to the real parser; a handwritten callback mock supplies sample bytes or a deliberate
source error. A source returning already-normalized products would bypass this model's validation
boundary and is not the selected mock contract.

Persist successful run metadata, immutable rule settings, and each normalized/transformed item.
Uploaded and sample file bytes remain transient. Keep no uploaded filename, arbitrary file path,
provider credential, browser-supplied workspace identifier, or raw request dump in these tables.
Preview and CSV export are reconstructed from the same completed stored rows.

## Schema and entity relationships

Use an application-owned PostgreSQL schema named `catalog_app`. Manage it through a separately
implemented explicit migration step; opening a connection must not implicitly create or alter it.

| Entity | Ownership and relationship |
| --- | --- |
| `catalog_app.workspaces` | Contains the one seeded demo workspace. |
| `catalog_app.processing_runs` | Belongs to a workspace; captures one synchronous processing attempt and its immutable settings. |
| `catalog_app.result_items` | Belongs to a run and the same workspace; records one input product's original normalized values, transformed values, and inclusion decision. |

The intended foreign keys are `processing_runs.workspace_id → workspaces.id` and the composite
`result_items(workspace_id, run_id) → processing_runs(workspace_id, id)`. The composite relationship
prevents an item's declared workspace from differing from its run's workspace. Every repository
read/write also includes the trusted workspace scope; global run-ID lookup is not an authorization
shortcut.

### Workspaces

| Field | Proposed database type | Contract |
| --- | --- | --- |
| `id` | `uuid`, primary key | Stable synthetic identity provisioned by the seed/migration contract. |
| `slug` | `text`, unique, not null | Fixed neutral slug `demo`; not supplied by the browser. |
| `created_at` | `timestamptz`, not null | Time the seeded record was created. |

Startup verifies that the configured demo workspace exists. An absent or mismatched seed prevents
readiness; a request does not silently create a new workspace. There is no membership, billing,
agency, or user table in this feature.

### Processing runs

| Field | Proposed database type | Contract |
| --- | --- | --- |
| `id` | `uuid`, primary key | Generated by Go for an admitted attempt. |
| `workspace_id` | `uuid`, not null | References the trusted demo workspace. |
| `source_kind` | `text`, not null | `sample` or `upload`. |
| `sample_id` | `text`, nullable | Required for `sample`, null for `upload`; a fixed catalog identifier, not file contents. |
| `title_prefix` | `text`, not null | Literal prefix, at most 64 characters, captured before processing. Empty is valid. |
| `exclude_unavailable` | `boolean`, not null | Captured rule setting; defaults false when omitted from a valid request. |
| `status` | `text`, not null | `processing`, `completed`, or `failed`. |
| `input_count` | `integer`, nullable | For completed runs, 1–1,000 normalized input items; otherwise null. |
| `included_count` | `integer`, nullable | For completed runs, number retained in preview/export; otherwise null. |
| `excluded_count` | `integer`, nullable | For completed runs, number excluded by the availability rule; otherwise null. |
| `started_at` | `timestamptz`, not null | Attempt start, after admission and trusted-workspace resolution. |
| `finished_at` | `timestamptz`, nullable | Set for a persisted terminal outcome. |
| `failure_code` | `text`, nullable | Safe machine-readable category for failed runs; null otherwise. |
| `failure_message` | `text`, nullable | Bounded user-facing explanation; no raw dependency exception or input excerpt. |
| `failure_details` | `jsonb`, nullable | Bounded issue objects as defined by the [API contract](contracts/catalog-api.md); no raw CSV. |
| `failure_details_truncated` | `boolean`, not null, default false | Whether issue objects were omitted from the bounded failure record; false for processing/completed runs. |

Add a unique key on `(workspace_id, id)` for the composite result-item foreign key. Proposed checks
constrain source kind, sample-ID presence, status, prefix length, nonnegative counts, and terminal
field combinations. A completed run requires all counts, `input_count = included_count +
excluded_count`, a finish time, and no failure fields. A failed run requires a finish time and failure
code; it has null counts. A processing run has no terminal time, counts, or failure fields.

Failure codes distinguish at least `validation_error`, `input_limit`, `source_unavailable`,
`database_unavailable`, `deadline_exceeded`, `cancelled`, and `interrupted`. Pre-admission failures
can return an API error without creating a run. Persistence failure can prevent recording a later
failure; never invent a persisted failed row in the response.

### Result items

Store one row for every valid input item, including products excluded by the rule. Exclusion is a
business decision on a valid product, not an invalid-row disposition.

| Field | Proposed database type | Contract |
| --- | --- | --- |
| `workspace_id` | `uuid`, not null | Same owner as the run. |
| `run_id` | `uuid`, not null | References the owning run through the composite foreign key. |
| `original_position` | `integer`, not null | One-based product-record position, excluding the header; 1–1,000. It is not necessarily the physical CSV line number. |
| `sku` | `text`, not null | Original normalized SKU, unique within this run; at most 128 characters. |
| `input_title` | `text`, not null | Original normalized title; at most 200 characters. |
| `price` | `numeric(18,4)`, not null | Nonnegative exact decimal value with up to 14 integer and four fractional digits. |
| `currency` | `text`, not null | Three uppercase ASCII letters. |
| `availability` | `text`, not null | `in_stock` or `out_of_stock`. |
| `output_title` | `text`, not null | Literal captured prefix plus original normalized title; at most 264 characters. |
| `included` | `boolean`, not null | False only when exclusion is enabled and availability is `out_of_stock`. |
| `exclusion_reason` | `text`, nullable | `unavailable` for excluded items; null for included items. |

Use `(workspace_id, run_id, original_position)` as the primary key and a unique key on
`(workspace_id, run_id, sku)`. SKU comparison is case-sensitive. Position and SKU uniqueness are scoped
to a run: another run may legitimately contain the same products.

Phase 1 transforms only title and inclusion. The unchanged SKU, price, currency, and availability
are shared normalized values for the input and output product views; duplicate output columns for
unchanged fields are unnecessary. The model still reconstructs both complete five-field views.

Apply database checks for nonnegative price, allowed availability, currency syntax, positive position,
length limits, and inclusion/reason consistency. Go performs the complete CSV and text validation
before persistence. The cross-table invariant that only completed runs possess result rows is
enforced by the repository transaction and verified later; foreign keys alone do not prove it.

## Normalization and deterministic output

The CSV grammar, limits, and two rules are governed by [FR-003 through FR-010](spec.md). Normalize
each input field by trimming surrounding whitespace, then validate every row before applying the
rules. Headers use the exact case-sensitive names after an optional leading UTF-8 BOM. Products are
not repaired through implicit currency conversion, identifier substitution, or field mapping.

Treat price as an exact decimal string at the application and JSON boundaries. Parse and compare it
without binary floating point; persist it as `numeric(18,4)`. Canonical serialization removes
unnecessary leading integer zeros and trailing fractional zeros, and omits an empty decimal point:
`12.3400` becomes `12.34`, `12.0000` becomes `12`, and `0.0000` becomes `0`. Exponent notation,
grouping separators, signs, more than four fractional digits, and values beyond the specified range
are invalid input. The database adapter must reject overflow or excess precision rather than rely on
PostgreSQL rounding a value into range.

Preserve prefix whitespace literally; prefix application does not mutate the original title. Reject
control characters in title/prefix and either a normalized or resulting title whose first
non-whitespace character is `=`, `+`, `-`, or `@` before success. Character limits count Unicode
characters, not UTF-8 bytes; the SKU grammar itself is ASCII. Reprocessing starts
from fresh original input, not an earlier transformed result.

The Go result projection reads rows ordered by `original_position`, keeps `included = true`, and
produces exactly `sku,title,price,currency,availability`, with `title = output_title` and canonical
decimal strings. Preview and CSV export consume that same projection. CSV escaping and LF line
endings are transport encoding, not a second set of transformations. A completed all-excluded run
has zero projected rows and a header-only export; it still retains all its valid input result rows.

## State transitions and transaction boundaries

1. **Admit:** reject malformed envelopes and excess request capacity, then validate rule settings
   in Go before inserting a run: prefix length, UTF-8 validity and control-character rejection must
   produce a `422` rule error rather than a database constraint error. Reject excess concurrency
   before starting work. Resolve the configured workspace and insert a `processing` run with
   immutable source/rule settings. There are no result rows yet.
2. **Process:** obtain raw CSV, enforce the byte/row bounds, parse, normalize, validate the complete
   input, apply the title and exclusion rules, and prepare the bounded result. All source bytes and
   intermediate data remain request-scoped. There is no detached worker or automatic retry.
3. **Complete atomically:** in one database transaction, lock/check the run is still `processing`,
   insert every result item, and set counts, `completed`, and finish time. Commit all these effects
   together. A partial insertion or failed completion update rolls back all result-item changes.
4. **Fail:** discard transient results and best-effort update only a still-`processing` run to `failed`
   with bounded safe details and the truncation flag. This conditional update must never overwrite an already committed
   completed result. Failed runs have no result rows or export.
5. **Read:** query by trusted workspace and run ID. Completed settings/results are immutable. A new
   request produces a new run; changing a UI control does not mutate an existing run.

Cancellation and the 30-second processing deadline propagate through source intake, processing, and
database work. Failure recording may use a short bounded cleanup operation, but does not continue
catalog processing or introduce a detached job. If completion committed before a disconnect or
cancellation was observed, the completed result stands.

A failed commit acknowledgment can leave the database outcome uncertain. Return a database error
unless completion can be established; do not claim rollback solely from a missing acknowledgment.
Best-effort failure recording targets only `processing`. A later known-ID lookup reports the actual
persisted outcome. The feature does not promise recovery of a run ID lost with the POST response.

During startup of the single Go instance, mark leftover `processing` runs `failed` with code
`interrupted` before serving processing requests. There is no resume and no retained raw CSV from
which to reconstruct the attempt. This startup policy is invalid for overlapping replicas and must
be redesigned before changing the single-instance deployment assumption.

## Future PostgreSQL/Supabase boundary

Keep `catalog_app` application-owned and non-exposed by default if the database later moves to a
Supabase-hosted PostgreSQL service. Schema naming alone is not an access control. The present design
does not use Supabase Auth foreign keys, Supabase functions, a Data API, or a claimed RLS policy.

A later move requires explicit migrations and tests against the actual service: schema exposure,
database roles/privileges, connection/pool behavior, extensions, authentication mapping, and any
chosen RLS policies. The trusted demo-workspace filter and composite foreign key do not establish
those future guarantees. Ordinary PostgreSQL migrations and application SQL are the Phase 1 boundary.

## Verification boundary

Model checks support the four scenarios in [spec.md](spec.md): H1 sample results and exact projection,
H2 equivalent upload plus restart retrieval, S1 whole-input rejection with no export, and S2 source
failure without false success. Atomic completion, conditional failure recording, interrupted-run
startup handling, and exact decimal serialization are supporting assertions, not additional product
journeys. No migrations or tests exist as a result of this document.
